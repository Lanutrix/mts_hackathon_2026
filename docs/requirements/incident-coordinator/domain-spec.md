# Доменный контракт

Источник: принятый контракт пользователя от 21.11.2026, основанный на PDF и переданных уточнениях организаторов.

## 5. Точная доменная модель

Исходная карта: `0/Assigned/Назначен`, `2/WorkInProgress/Выполняется`, `7/Resolved/Завершён`, `10/Closed/Закрыт`, `20/Research/Исследование ситуации`. Приоритеты возрастают по серьёзности: 1 низкий → 4 наивысший. Не вводи обратное P1=critical без явного mapping, лучше показывай исходные названия.

Чистые функции группировки, одинаковые для API, UI и тестов:

```text
active = stateId in {0, 2}
coordinatorTeam = assignedGroupName после нормализации пробелов
                  == "КЦ ИТ Координаторы Массовых Инцидентов"
critical = active && priorityId == 4
coordinators = stateId in {0, 2, 20} && coordinatorTeam
high = active && priorityId == 3
research = stateId == 20
```

Не объединяй эти группы через else-if. Research может одновременно быть у координаторов, но никогда в активных critical/high. 7/10 не входят в активные группы; доступны в истории и недавних решениях. Для isNeedUp=true показывай бейдж/фильтр без придумывания ещё одной обязательной группы. Неизвестные/конфликтующие статусы должны быть заметны в диагностике, а не исчезать. Общий unique count не равен сумме групп.

При конфликте известных stateId/stateEnum сохраняй raw, помечай запись как неподтверждённую и выводи в заметный блок качества данных до сверки; не присваивай ей автоматически одну из четырёх групп. Некорректная подпись priority при валидном priorityId исправляется только в нормализованном отображении с предупреждением. Различай такие дефекты от ошибочного справочника, для которого карта 7/10 уже однозначно исправлена.

Уведомления создаются по переходам, а не при каждом render: новое active critical/повышение до 4, новое назначение координаторам включая Research, решение ранее активного critical, возврат в active critical. Один переход с несколькими причинами объединяется. Dedup key включает identity, принятую revision и тип события. Initial load показывает текущие важные записи без исторического звукового шторма. Решение critical остаётся в постоянной ленте и конфигурируемом блоке недавних решений, например 15 минут; статус не исчезает бесследно. Для перехода в Research без completionDate не выдумывай время решения. Прочтение уведомления не равно ACK команды и не меняет ITSM state. Звук/браузерные notifications требуют пользовательского включения; визуальное уведомление доступно всегда.

Исходный набор должен дать **0 / 2 / 1 / 5** в порядке critical/coordinators/high/research. Это независимый контроль результата.

Внешний контракт — исходный массив. Сохраняй все 46 полей: sysId, id, state, stateEnum, stateId, stateReason, stateReasonId, submitDate, deadline, completionDate, lastAssignmentToTeamDateTime, header, description, shortDescription, assignedGroupName, assignedEmployee, assignedEmployeeLogin, initiatorName, initiatorLogin, isEffect, isReason, isDouble, isMaster, incType, serviceTypeId, serviceType, priorityId, priority, urgencyId, urgency, impactId, impact, waitingExitDate, isRootIncident, productName, productId, productMasterId, productUrl, service, serviceId, scenarioName, isNeedUp, eliminationType, eliminationTypeId, receivingChannel, solution. Дополнительные будущие поля тоже сохраняй.

Идентичность: namespace источника + строковый sysId, fallback строковый id с диагностикой. Уникальность id проверяй отдельно. Не округляй 18-значные ID. Не объединяй продукты/инциденты по повторяющемуся productId из демонстрационных данных.

Сроки: сохраняй source deadline; изменение приоритета не сбрасывает и не пересчитывает срок. При null — «Срок не задан». SubmitDate означает регистрацию, не доказанное время возникновения. CompletionDate — историческое завершение; не равняется закрытию. Нулевая waitingExitDate превращается в null только в нормализованном представлении. UTC instants хранятся без потерь; UI по умолчанию Europe/Moscow с явной зоной и возможностью настройки. Не угадывай timezone timestamp без offset: отклони либо используй явно заданную timezone источника с quality flag.

Solution не управляет статусом. Сохраняй raw и историю, активный solution показывай как несогласованный/предыдущий текст. Не используй его как verified training label. isNeedUp null — неизвестно. Названия isEffect/isReason противоречат интуитивной трактовке справочника: не выводи направление связи без дополнительной информации. Master/Double не дают ID родителя. ProductUrl не является ссылкой на инцидент.

Оригинальные snapshot-переходы могут пропускать промежуточные статусы. Не отбрасывай валидный снимок только потому, что мы не видели промежуточный этап. В деморедакторе разреши документированные переходы 0→2, 2→7, 7→0/2/20/10, 20→2/10 как проектную политику; 10 терминален, повтор — новый ID. Внешний Closed→active под тем же ID пометь конфликтом identity/lifecycle и запросом сверки, не исправляй исходник.
