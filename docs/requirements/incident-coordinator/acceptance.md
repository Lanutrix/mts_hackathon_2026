# Проверки и критерии приёмки

## 11. Синтетические данные

Генератор должен выпускать JSON в исходном формате и отдельный manifest с seed, generatorVersion, fixedClock, hashes, expected groups/events и перечнем покрытых сценариев. Oracle ожидаемого поведения держи отдельно от production grouping-функций: тест не должен просто повторять проверяемую реализацию.

Наборы:

- `original-check`: исходные 44 записи как read-only fixture там, где это разрешено; контроль 0/2/1/5.
- `acceptance`: не менее 120 комбинаций 5 статусов × 4 приоритета × 2 назначения × 3 serviceType, плюс граничные и негативные случаи.
- `demo`: около 600 понятных синтетических записей, без реальных ФИО, телефонов, email и контактов команд. Новые ID с понятным DEMO namespace; metadata вне обязательного массива.
- `load`: 2 000 записей для целевой интерактивности и 10 000 для нагрузки/виртуализации. Для генератора используй seed 42, 43, 44 и независимый holdout.

Все количества — проектные ориентиры, не статистика МТС. Не делай весь набор случайным: обязательные случаи добавляй явно, остальные — seeded generation. Варианты deadlines: просрочен, ровно now, через секунду, близко, далеко, null, malformed, без timezone. Timestamps: разные offset, ночь/смена даты, leap day, completion до submit как отрицательный тест, сохранённая completionDate после reopen.

Покрой булевы true/false/null, unknown enums, отсутствующие ключи, большие строковые ID, конфликт id/sysId, дубли, перестановку записей, большой/пустой/некорректный файл, нулевую дату, длинный кириллический текст, Unicode, HTML, prompt injection, malicious URL. Не помещай реальные секреты даже в негативные fixtures.

Event scripts: появление critical; coordinator assignment; обе группы; смена команды; priority вверх/вниз; отдельная смена срока; Resolved→reopen; Research+high/critical; Research+coordinators; Closed→новый ID; storm; file missing/partial write/rename; исчезновение записи; A→B→A; restart; SSE disconnect; AI timeout/старый ответ; repeat import/export. В live demo генератор сдвигает даты только в новой синтетической копии, исходник не переписывает.

Для расширений используй отдельные channel fixtures и независимые truth labels. Не обучай/оценивай routing на одинаковых шаблонах в train/test; grouping по эпизодам/семействам предотвращает утечку. Шаблонный delay симулятора не выдавай за измеренное человеческое время реакции.


## 12. E2E, качество и итеративные исправления

Проверяй снизу вверх: pure domain unit tests → file/DB integration → API/auth/SSE → пользовательские E2E → visual/a11y → нагрузка → staging/deployment smoke. Конфигурация CI воспроизводима и использует lockfile. Реальные данные и секреты не попадают в screenshots, traces или CI artifacts; при необходимости используй полностью синтетическую тестовую среду.

Каждому F01–F36 соответствует хотя бы один исполняемый E2E/интеграционный сценарий по характеру действия, с точными assertions. Каждому реализованному F37–F40 тоже нужен тест. Для обязательной демонстрации отдельный процесс меняет файл, браузер ожидает изменения UI без page.reload. Не подменяй это перезаписью React state или прямой вставкой в БД. Два browser contexts проверяют согласованность обновлений.

Playwright: устойчивые role/name/test IDs; auto-wait и ожидаемые условия вместо произвольных длинных sleep. Chromium — полный обязательный набор; Firefox/WebKit — ключевые потоки загрузки, обновления, навигации, уведомлений, layout и auth. 390/1024/1440/1920/2560 viewport, keyboard only, zoom, reduced motion, offline/reconnect. Детерминированный clock для границ deadline, реальные latency measurements отдельно. Для каждого дефекта сохрани failure trace/screenshot и исправление с regression test.

Критерии:

1. Группы на независимом oracle совпадают в 100% детерминированных случаев; исходный пример 0/2/1/5.
2. Нет rounding идентификаторов, потери полей при roundtrip, фиктивного закрытия по solution/исчезновению/monitoring resolved.
3. Повторы/formatting/reconnect не плодят уведомления; A→B→A не теряется. Initial load не даёт исторического шторма.
4. Все обязательные действия работают с клавиатуры; нет critical/serious a11y нарушений в автоматическом прогоне, а ручные контраст/focus/reading-order проверки задокументированы.
5. Цель проекта: p95 от стабильной записи файла до обновления UI ≤2 секунды на 2 000 записях в указанной среде. Измеряй watcher/read/commit/stream/render отдельно; не выдавай цель за достигнутое значение. На 10 000 записях запиши фактический результат и ограничения.
6. AI smoke действительно вызывает выбранную модель/ML; данные и основания корректны; при отказе обязательная часть UI продолжает работать. Mock pass не закрывает live-AI acceptance.
7. Нет console errors, бесконечных запросов, hydration/runtime ошибок, event-listener leaks или растущего без причины потребления памяти после длительного wallboard прогона.
8. Серверная авторизация блокирует запрещённые операции; source path/URL проверяются; injection не выполняется; ни один секрет не присутствует в клиентской сборке, репозитории, логах и артефактах.
9. Проверены restart, rollback и восстановление backup в отдельном тестовом пространстве.

Цикл исправлений: воспроизвести → определить причину → исправить минимально → добавить/уточнить regression test → повторить затронутые тесты → полный обязательный прогон перед релизом. Не ослабляй assertions и не отключай тест ради зелёного статуса. После стабилизации останови необоснованные повторы; продолжай к деплою. Если внешняя зависимость блокирует тест, status=blocked с причиной и последним evidence, не pass.

Создай `docs/qa/flow-coverage.csv`, `docs/qa/test-report.md`, `docs/qa/defects.md`, `docs/qa/performance.md`. В coverage: flow/requirement, fixture/seed, viewport/browser, test file/name, last run, status, evidence. Все F01–F40 перечислены, включая честно deferred расширения. Не заявляй проверку всех мыслимых комбинаций; докажи все обязательные классы и описанные границы.
