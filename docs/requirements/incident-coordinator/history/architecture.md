# Контекстная архитектура и предварительные контракты

**Статус:** проектная гипотеза по встрече. Форматы здесь предложены, а не получены от МТС.

## Уровень 0: топология

Инициаторы (автоматические алерты / клиенты / сотрудники / боты) ↔ **IN** → **ANL** ↔ история, правила, реестр команд → **OUT** ↔ команды и инициаторы. **UI** наблюдает за статусом и позволяет человеку вмешиваться. Сквозные функции: журнал событий, контроль SLA, авторизация, уведомления.

## Уровень 1: компоненты и границы

### IN: приём и нормализация
- Адаптеры для событий мониторинга, агрегированных жалоб и ручных обращений.
- Валидация обязательных полей, нормализация форматов, привязка источника, идентификатора внешнего события и времени регистрации.
- Дедупликация и корреляция **как вопросы для исследования**, а не уже утверждённые функции.
- Синтетические события через те же контракты, что и реальные адаптеры.

### ANL: принятие решений
- Определение типа инцидента, затронутых сервисов, влияния, приоритета и команды.
- Сроки 2/6/12 часов упоминались на встрече; условия назначения и пересчёта — открытый вопрос.
- Поиск похожих случаев и исторических **фактически подтвердивших решение** команд.
- Протокол объяснения решения, оценка уверенности, передача спорного случая человеку.
- Триггеры на события: смена статуса, таймаут подтверждения, риск нарушения SLA, ошибочная маршрутизация.

### OUT: двусторонняя передача
- Адаптеры исполнителей: выдача, подтверждение получения, отклонение/перенаправление, прогресс, сообщение об устранении.
- Обратная связь с исходным инициатором для подтверждения, что проблема исчезла.
- Нельзя считать доставку сообщения доказательством принятия работы.

### UI: рабочее место
- Очередь/таблица, быстрые фильтры, сортировка по близости дедлайна, видимые статусы и таймер.
- Карточка инцидента с причиной маршрутизации, историей действий, сообщениями, способами вмешательства.
- Подготовка к нескольким координаторам (разграничение видимости/назначение), хотя на демо может быть один.

## Предлагаемая сущность Incident (не утверждённая схема)

| Группа | Поля-кандидаты |
|---|---|
| Идентичность | incident_id, external_event_id, created_at, updated_at |
| Источник | initiator_type, initiator_id, source_channel, source_reference |
| Содержание | title, description, incident_type, affected_services, impact |
| Управление | priority, sla_policy_id, deadline_at, status, owner_coordinator_id |
| Исполнение | assigned_team_ids, assignee/acknowledgement timestamps |
| Качество | classification_confidence, routing_rationale, related_incident_ids |
| Доказательства | evidence_refs, resolution_summary, verified_by, verification_at |
| Аудит | events с actor, timestamp, action, before/after, reason |

Требуются типизация, ограничения, валидация, модель прав и точный жизненный цикл. История назначения **не должна** подменять историю фактического разрешения.

## Нефункциональные направления исследования

Задержка первичной маршрутизации, корректность назначения, надёжная обработка повторных событий, безопасность данных клиентов, наблюдаемость действий агента, идемпотентность и масштабируемость. Целевые значения не выдумывать — сформировать и обосновать аналитически.
