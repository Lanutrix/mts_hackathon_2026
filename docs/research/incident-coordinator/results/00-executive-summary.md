# 00. Executive summary — интеллектуальный координатор инцидентов

**Дата исследования:** 20.11.2026 · **Статус:** аналитическая основа для MVP, не утверждённое ТЗ МТС · **Версия:** 1.0  
**Следующие документы:** [процесс](01-domain-and-process.md) · [контракты IN](02-input-channels-and-data.md) · [метрики](09-quality-evaluation-and-risks.md) · [вопросы Q01–Q25](10-open-questions-answered.md) · [источники](sources.md).

## Решение в одном абзаце

**[Рекомендация]** Создать *human-supervised incident routing platform*, а не «чат-бота, самостоятельно чинящего инфраструктуру»: адаптеры IN приводят разнотипные сообщения к канонической схеме; ANL применяет правила владения сервисами и ранжирует команды по проверяемым признакам/истории; OUT фиксирует отправку, **отдельное принятие ответственности (ACK)** и обратную связь; UI ускоряет работу координатора; append-only event log измеряет каждый этап. Автоматическое назначение допускается лишь по белым спискам правил, при остальных случаях — обоснованный выбор с override. Автоматическое вмешательство в системы исключить из базового MVP.

## Что подтверждено и что нет

| Статус доказательности | Положение | Основание |
|---|---|---|
| **Участники** | Цель — снизить время реакции; IN → ANL → OUT + UI; «память» успешных и ошибочных маршрутов; несколько координаторов; явное подтверждение инициатором | [152](../../../meetings/2026-11-20/transcripts/recording-152.md), [153](../../../meetings/2026-11-20/transcripts/recording-153.md), [154](../../../meetings/2026-11-20/transcripts/recording-154.md), [D01–D14](../../../requirements/incident-coordinator/decision-log.md) |
| **Участники, не регламент** | Три «типа инцидентов», предполагаемые каналы, дедлайны **2/6/12 часов**, частые кейсы (распознано «PILA»), команды по сервисам/оборудованию | [запись 153](../../../meetings/2026-11-20/transcripts/recording-153.md); распознавание термина «PILA» ненадёжно |
| **Подтверждённый внешний факт** | В отраслевых руководствах координацию отделяют от операционного устранения; ACK отличают от resolution | [Google SRE, Incident Response, S01](sources.md#s01); [PagerDuty, S06](sources.md#s06) — **не доказательства устройства МТС** |
| **Пробел данных** | Реальные SLA/точка старта часов/паузы, каталог команд, интеграции, права доступа, история тикетов, схемы статусов и существующий baseline | [Q01–Q25](../../../requirements/incident-coordinator/open-questions.md), [ответы](10-open-questions-answered.md) |
| **Рабочая гипотеза** | Синтетический реестр из пяти команд, 3 приоритета, демонстрационные дедлайны, web-форма + mock-alert + aggregate complaints, симулятор ACK | [план MVP](08-mvp-demo-and-synthetic-data.md) |

**Не делать:** заявлять сокращение SLA или экономию часов МТС по синтетике, автоматически сбрасывать дедлайн при смене приоритета, подменять успешным первым назначением окончательную команду, считать delivered == acknowledged, публиковать реальные обращения/секреты.

## Система метрик: что именно улучшаем

Основная метрика для проверяемого MVP — **time to valid team ACK**: `t_ack_first_valid_owner - t_actionable_received`, где валидный владелец — команда, подтвердившая ответственность и являющаяся корректной по независимой разметке. При наличии отдельного обязательного регламента можно уточнить официальное определение «реакции»; пока это **операциональная гипотеза**, а не SLA МТС.

Разложение времени: получение события → нормализация → ожидание триажа → выбор/проверка команды → отправка → доставка → ACK. Отдельно показывать `time_to_triage`, `time_to_first_assignment`, `reassignment_rate`, `time_to_verified_close`. Время закрытия **не заменяет** метрику реакции. [Формулы и дизайн эксперимента](09-quality-evaluation-and-risks.md).

## Сравнение MVP и baseline

| Контур | Контрольное состояние | Эксперимент |
|---|---|---|
| Без интеллектуального ускорения | Координатор вручную выбирает команду по одному и тому же каталогу/событиям | Предзаполненные признаки + объяснимый ranking; идентичные сценарии |
| Корректность | Финальная подтверждённая компетентная команда с независимым ground truth | Top-1/Top-3, rate misroute, abstain, правки человека |
| Измерение | Одни и те же сценарии/семена, рандомизированный порядок показа, фиксированный clock | Пары значений, медианы, p90, bootstrap CI; без заявления реального выигрыша |
| Отказоустойчивость | Потеря интеграции, дубликаты, ошибки | Повторный delivery без повторного назначения; DLQ и журнал |

**[Пробел]** В репозитории нет материалов для эмпирического измерения времени людей на реальных обращениях; отраслевые цифры ускорения поэтому **не приводятся**.

## Приоритетное решение

1. **P0:** утвердить дефиницию реакции, типы и часы SLA, право закрытия, минимум схем IN/OUT, владельца решения по маршруту.
2. **P0:** реализовать event timeline, schema validation, каталог владения, rule-based baseline, ручной override, ACK и verification, воспроизводимое демо.
3. **P1:** TF-IDF/embedding rerank поверх жёстких ограничений, исправление неверных маршрутов, конфигурируемые часы, multi-coordinator concurrency, тестирование.
4. **P2:** RAG, голос, продуктивные корпоративные интеграции и автоматическое устранение — только после разрешения на данные и дополнительных проверок.
