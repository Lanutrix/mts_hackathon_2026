# Как «Срез» разбирает инциденты

Координатору нужны три разных ответа. Что проверить первым? Какие обращения разумно разбирать вместе? На каких записях основан совет? Эфир отвечает на первый вопрос порядком очереди, на второй — подборками, на третий — ссылкой на заявку и исходное поле. Помощник использует тот же источник и дополнительно может считать по завершённым заявкам.

## 1. От выгрузки до экрана

1. Обработчик читает JSON-массив выбранного источника. Для полного снимка пределы составляют 20 МиБ и 20 000 записей. Ошибка JSON, повтор идентификатора или недопустимая структура отклоняют весь снимок. Эфир продолжает использовать последнюю принятую ревизию.
2. Внутренний ключ состоит из источника и точного строкового `sysId`. При отсутствии `sysId` используется строковый `id` со своей меткой. Хеш записи — SHA-256 канонического JSON, хеш снимка вычисляется по отсортированным парам «ключ, хеш». Перестановка строк и ключей объекта не создаёт новую ревизию.
3. Нормализация проверяет коды статуса и приоритета, типы полей, часовые пояса и порядок дат. Исходный JSON остаётся доступным в карточке. Ошибка уровня `error` исключает запись из автоматической классификации. Заполненное поле решения у активной заявки само по себе не завершает инцидент. Отсутствие в следующей выгрузке отмечается отдельно от закрытия.
4. Изменения карточек, события, уведомления и указатель принятой ревизии записываются транзакционно. Только после фиксации сервер посылает событие обновления. Браузер запрашивает свежий срез со своими фильтрами. Переход срока пересчитывается по времени даже при неизменном файле.

Администратор может добавить одну заявку или пакет через форму, вставкой JSON или файлами. Сервер проверяет весь пакет, идентичные повторы учитывает отдельно, конфликт отклоняет целиком. Запись в рабочий файл выполняется под блокировкой с проверкой исходного снимка и атомарной заменой. Учебная симуляция, демо и рабочая копия имеют отдельные пространства данных.

## 2. Какие заявки попадают в эфир

| Сигнал | Условие по полям ITSM |
| --- | --- |
| Критические | `stateId ∈ {0, 2}` и `priorityId = 4` |
| Высокий приоритет | `stateId ∈ {0, 2}` и `priorityId = 3` |
| У координаторов | `stateId ∈ {0, 2, 20}` и назначена группа «КЦ ИТ Координаторы Массовых Инцидентов» |
| Исследование ситуации | `stateId = 20` |

Сигналы пересекаются. Назначенная координаторам критическая заявка учитывается один раз в общем числе. Просрочка означает, что известный срок уже прошёл. Близкий срок — от текущего момента до 15 минут включительно. Отсутствующий срок даёт отдельную категорию. Потребность в устранении последствий учитывается только при `isNeedUp === true`.

**Порядок реакции.** Каждая заявка получает одну позицию по первому подходящему правилу. Исчезнувшая из источника заявка сразу переносится на сверку, в конец очереди. Для остальных порядок следующий.

| Очерёдность | Основание |
| --- | --- |
| 1 | Критическая заявка с истёкшим или близким сроком |
| 2 | Остальные критические |
| 3 | Срок истёк |
| 4 | Срок наступит в ближайшие 15 минут |
| 5 | Требуется устранение последствий |
| 6 | Заявка у координаторов либо команда отсутствует |
| 7 | Идёт исследование ситуации |
| 8 | Проверка хода работ |
| 9 | Требуется сверить исчезнувшую запись с источником |

Внутри одной позиции сравниваются ближайший срок, затем приоритет по убыванию, затем номер заявки с числовой сортировкой. Поэтому поступление сотен менее срочных заявок не отодвигает отдельный критический инцидент. Один и тот же набор полей при одном времени расчёта даёт воспроизводимый порядок.

## 3. Как образуются подборки и подсказка эфира

В режиме семантических групп сервер извлекает признаки из текста заявки. Например, «авторизация» описывает область, «отказ» — проявление. Из устойчивых сочетаний и повторяющихся фраз сразу получается локальная подборка. Для уточнения модель получает словарь признаков и до 128 профилей с диапазонами количества и критичности. Сначала отбираются профили с критическими заявками, затем более частые. При изменении входного набора расчёт проверяется повторно. Совпадение профиля позволяет использовать кеш.

Для предложенного моделью объединения проверяются допустимые признаки, ссылки на профили, название и иконка. Неохваченные заявки сохраняют локальную группировку. Отдельно доступны фиксированные срезы по команде, продукту, приоритету и сроку. Совпадение симптомов даёт повод сверить случаи. Подтвердить общий сбой или первопричину можно только по материалам расследования.

**Совет по заявке.** У ведущей заявки выбирается поле, которое объясняет следующий ручной шаг. Например, после истечения `deadline` координатору доступно предложение уточнить срок. Этот шаг уже есть в ответе дашборда. Пока готовится формулировка ИИ, координатор может читать основание и открыть заявку. Модель получает состояние полей и агрегаты выбранной группы. Сгенерированный текст проходит проверку ссылок на факты, чисел и смысла действия. При смене заявки или основания устаревшая формулировка не должна заменять новый совет. При отсутствии подтверждённого текста сохраняется подсказка по полям ITSM.

**Долька в эфире.** Знаменатель — число уникальных наблюдаемых заявок после выбора сигнала и фильтров. Сектор мякоти занимает угол `π × просроченные / всего`. Четыре полные косточки соответствуют 100% заявок с отметкой об устранении последствий. Площадь неполной косточки пропорциональна остатку. Например, при 3 заявках из 8 видны одна полная косточка и вторая половинной площади. Точные количества доступны в подписи индикатора. При пустой выборке отображается контур. Выбор отдельной подборки раскрывает её реестр и сохраняет общую картину текущего эфира.

Подтверждённый совет эфира хранится в памяти открытой сессии до минуты. При возврате из карточки он доступен сразу, если источник, запуск симуляции и основание совета совпадают. Изменение значимых полей меняет ключ расчёта. На карточке координатор получает предварительные варианты команды и комментария вместе с данными маршрутизации. Их можно использовать сразу. Запрос к модели начинается при открытии подсказок. Выбор варианта заполняет форму, а для сохранения решения требуется подтверждение координатора.

## 4. Как помощник выбирает вычисление и канву

1. Сервер определяет источник, пользователя, снимок и, при продолжении диалога, предыдущий результат. В расчёт берутся уникальные присутствующие записи без ошибок, исключающих их из анализа. Общая рабочая очередь и вся выгрузка — разные выборки. Например, для времени решения нужны также завершённые заявки.
2. Запрос разбирается на операцию, показатель, поле группировки, ограничения, период, порядок и число результатов. Упоминания номера или названия сопоставляются с сущностями источника. Явный порядок регистрации применяется к дате регистрации, запрос о длительности — к паре дат. Число из номера заявки не используется вместо времени.
3. Для поддерживаемых формулировок план строится на сервере. В других случаях модель может предложить структурированный план. Сервер проверяет его по контракту допустимых операций и параметров. Числа рассчитывает исполнитель по записям. Справочные вопросы получают ответ из предметной справки. При недостатке данных или невозможности однозначного разбора возможны уточнение и объяснение ограничения.
4. Тип результата определяет представление. Счётчик показывает одно число, порядок регистрации — карточки с датами, частоты — рейтинг, длительности — число или сравнение, связи — схему с основанием каждого ребра. Источники можно открыть. Пользователь также может явно сменить форму поддерживаемого результата.
5. Токен предыдущей реплики и идентификатор показанной выборки дают смысл словам «из них» или «а у второй команды». Сервер связывает их с пользователем, источником и запуском симуляции. Срок жизни серверной выборки — 15 минут, число сохранённых выборок ограничено. Если выборка недоступна, её можно запросить повторно.

| Вопрос координатора | Что нужно проверить в ответе |
| --- | --- |
| «Покажи самый первый инцидент» | Минимальный корректный `submitDate`, номер, заголовок и карточка. При одинаковом времени порядок определяется номером |
| «Какое среднее время решения?» | Среднее по завершённым измеримым заявкам, количество учтённых записей и пояснение исключений |
| «Сколько в среднем проходит между сменами статуса?» | Среднее по интервалам журнала, количество интервалов и заявок. При отсутствии наблюдений выводится сообщение о нехватке истории |
| «А медиана?» после вопроса о сменах статуса | Медиана всех наблюдаемых интервалов той же выборки. Например, интервалы в 5, 8 и 13 минут дают медиану 8 минут и среднее 8 минут 40 секунд |
| «Среднее время решения по продуктам», затем «а медиана?» | Для каждого продукта остаётся та же выборка. Меняются агрегат и порядок по рассчитанному значению. Доступны также команда, симптом, текущий статус и приоритет |
| «У какой команды больше всего заявок?» | Количество по каждой команде в обозначенной выборке и рейтинг |
| «Что общего у этих двух инцидентов?» | При наличии двух идентификаторов — схема прямых упоминаний и совпадений полей. Если пары ещё нет, помощник может запросить номера |
| «Что такое инцидент?» | Краткое определение и переход к тематической справке |

### Регистрация, время решения и переходы статуса

«За последние 48 часов» задаёт скользящее окно от момента среза. «20 ноября» задаёт календарные сутки в Москве. Для «среднего времени» без контекста помощник указывает выбранную метрику — время решения — и предлагает отдельно посмотреть переходы статуса. Если уже обсуждались переходы, короткое уточнение сохраняет их смысл.

**Порядок регистрации.** Заявки без даты регистрации исключаются. Оставшиеся даты упорядочиваются в запрошенном направлении, после этого применяется ограничение количества. Календарные периоды среза учитывают московскую границу суток. Дата окончания выборки ограничена моментом расчёта.

**Время решения.** Для завершённой или закрытой заявки (`stateId ∈ {7, 10}`) длительность `dᵢ = completionDateᵢ − submitDateᵢ`. Нужны две корректные даты и неотрицательная разность. Период измерения определяется по дате завершения. Среднее равно `Σdᵢ / n`, где `n` — число измеримых заявок. Медиана берётся из отсортированных значений, при чётном количестве усредняются два центральных. Если в выборке три измерения 1, 3 и 8 часов, среднее равно 4 часам, медиана — 3 часам. Отсутствующая дата не превращается в ноль.

**Смена статуса.** Из журнала ревизий выбираются наблюдаемые переходы одной заявки. Если в 10:00 зафиксирован переход «Назначен» в «Выполняется», а в 10:25 — «Выполняется» в «Исследование ситуации», получаем один интервал 25 минут. Между концом предыдущего перехода и началом следующего должно совпадать состояние. Пропуск источника или недействительное состояние разрывают цепочку. Итог равен сумме длительностей, делённой на число интервалов. Один статический снимок не даёт измерения. Время фиксации описывает наблюдение стенда и может отличаться от фактического момента изменения в ITSM.

**Связи.** Явная ссылка на идентификатор в специальном поле или точное упоминание в описании даёт направленную связь. Совпавший продукт, сервис, команда или распознанный симптом даёт общую характеристику. Интерфейс показывает поле-основание, чтобы координатор мог различить эти ситуации.

### Голосовой вопрос

Микрофон включает распознавание русской речи в поддерживаемом браузере. Промежуточные слова отображаются во время диктовки, подтверждённый фрагмент добавляется в черновик. Можно отредактировать текст и отправить его обычной кнопкой. Эндпоинт помощника получает тот же текстовый запрос, что при вводе с клавиатуры. Браузер может использовать внешнюю службу распознавания, для этого требуется разрешение на микрофон. [Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)

## 5. Карточка, назначение и оповещения

Карточка соединяет исходные поля, журнал изменений и разбор с указанием оснований. Для рекомендации команды сервер рассматривает другие заявки. Порядок кандидатов определяется числом совпадений и по продукту, и по симптому, затем совпадениями по симптому, затем по продукту. При наличии совпадений предпочтение отдаётся профильной команде. Для исполнителя учитываются похожие случаи и текущая открытая нагрузка. Текущая заявка не служит доказательством своей же маршрутизации.

Координатор проверяет команду, исполнителя и черновик комментария. Подтверждение сохраняет решение в журнале платформы с автором и временем. Для применения назначения в ITSM предусмотрена ручная передача. В карточке можно сверить исходный JSON.

Первый импорт устанавливает исходное состояние. На последующих ревизиях журнал фиксирует появление критической заявки, возврат завершённой критической в работу, её завершение или переход к координаторам. Несколько причин одного события могут относиться к одной заявке. Состояние прочтения хранится для конкретного пользователя. Доставка на устройство дополнительно зависит от подписки браузера и разрешения на уведомления.

## 6. Учебная нагрузка и проверка

Учебный поток воспроизводит разную интенсивность по часам. Из обучающего журнала выбирается день того же типа, будний или выходной. Внутри каждого часа поступления распределяются случайно. Модель выбирает категорию с учётом часа и типа дня, затем первичную группу по категории со сглаживанием редких наблюдений. Ускорение ×30 даёт один модельный час за две реальные минуты. Отдельный сценарный инцидент показывает переходы жизненного цикла. Данные о поступлениях не измеряют производительность команд. [Модель и проверка на отложенном месяце](https://github.com/Lanutrix/mts_hackathon_2026/blob/feat/watermelon-dashboard-20261121/docs/implementation/incident-arrivals.md)

Из корня репозитория можно выполнить проверки следующими командами.

```sh
node --import tsx --test --test-concurrency=1 tests/canvas-semantic-time.test.ts tests/canvas-facts.test.ts tests/canvas-durations.test.ts tests/triage.test.ts tests/semantic-triage.test.ts tests/ingestion.test.ts
npm run build
npx playwright test tests/e2e/workflows.spec.ts -g "dictation"
```

Формулы, маршрутизацию и UI удобно сверять раздельно. Для первого инцидента можно самостоятельно отсортировать даты в выгрузке. Для среднего — выписать число учтённых заявок и сумму длительностей. Для совета — открыть указанную карточку и сверить конкретное поле. Для смен статуса нужен журнал хотя бы двух последовательных переходов одной заявки. Пустая очередь, одновременный пакет и последовательное поступление упражняют разные пути обновления. Подробности реализации находятся в [предметных правилах](https://github.com/Lanutrix/mts_hackathon_2026/tree/feat/watermelon-dashboard-20261121/packages/domain), [сервере аналитики](https://github.com/Lanutrix/mts_hackathon_2026/tree/feat/watermelon-dashboard-20261121/apps/server) и [автоматических проверках](https://github.com/Lanutrix/mts_hackathon_2026/tree/feat/watermelon-dashboard-20261121/tests).
